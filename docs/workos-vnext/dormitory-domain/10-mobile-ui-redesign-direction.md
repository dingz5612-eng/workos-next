# vNext 宿舍移动 UI 重设计方向

## 设计锚点

本文件定义 Work OS vNext 宿舍经营域的移动端 UI 重设计方向和高保真准入。它只约束 vNext 设计包，不修改当前 OAM Source Authority、generated、runtime、surface 或 tests。

旧 WorkOSNext mobile surface UI 不再作为 vNext 的视觉来源。旧 UI 只能作为问题审计对象，用来识别哪些体验不能继承。

当前 `outputs/workos-vnext/dormitory-ui-prototype/` 是 `rejected local draft`。它不得提交为 vNext 基线，不得作为 demo、验收件、高保真方向或后续视觉继承来源。

## 不继承旧 UI

vNext 不继承：

- 旧后台式视觉密度。
- 大面积堆叠卡片。
- 内部编号主显示。
- 字段大表单。
- 手填替代对象选择器。
- 动作字段混入表单。
- 三语言长文案挤压主按钮。
- 移动端底部遮挡或关键操作被吞没。
- 只显示成功、不说明下一步。

旧 UI 中仍可保留为约束的只有：当前业务事实、现有权威边界、真实运行问题和验收教训。

## 新 UI 定位

vNext 宿舍移动端是工作台型业务办理界面，不是营销页，也不是 PC 后台缩小版。

已确认的高保真方向是 **Executive Quiet Operations**：克制、贵气、专业、清晰，像企业级移动经营系统，而不是普通后台、财务软件或低端 SaaS 模板。

视觉基调：

- 象牙白、石墨黑、雾灰、香槟金、钛银、少量深墨蓝。
- 风险、阻断和异常使用酒红或铜色。
- 禁止绿色、青绿色、薄荷绿用于成功、可用、完成、通过、按钮、标签、图标、图表或任何状态。
- 成功与可办理状态用结构、图标、文字、香槟强调或钛银勾选表达，不依赖绿色。
- 默认中文单语言展示，不做多语言同屏；俄语和吉语只作为语言切换能力与布局压力规则。

目标体验：

- 移动端优先。
- 一眼知道正在办理什么。
- 系统带出的信息足够清楚，用户少录入。
- 固定选项用选择器，不手填。
- 金额、币种、业务对象和财务状态始终同屏可见。
- 证据缺失、阻断原因和下一步清楚。
- 三语言可读，长文案可换行、可收起、不遮挡。
- 页面有办理节奏，主按钮唯一且符合当前状态。
- 命令搜索是核心入口，可以识别对象和意图，并推荐办理项，但搜索本身只读、不写事实。
- 字段更厚但输入更少，页面优先展示对象摘要、只读上下文、证据、财务边界、阻断原因和下一步承接。

## 信息层级

每个高保真页面必须按以下层级组织：

1. 顶部任务条：当前办理项、状态、责任角色。
2. 主对象摘要：住客/企业/员工、住宿单、房间床位或费用依据。
3. 上游只读摘要：来源、主体解析、员工关系、财务回执、证据状态。
4. 当前输入区：本次要填的少量字段。
5. 固定选择区：房间、床位、币种、原因、证据类型、状态。
6. 财务边界区：金额、币种、收付方向、阶段语义、业务对象、财务承接状态。
7. 证据区：必需证据、缺失、驳回、过期、补交入口。
8. 阻断与下一步：缺什么、谁处理、处理后去哪。
9. 底部动作区：唯一主按钮、辅助动作、不可处理原因。

## 组件原则

| 组件 | 用途 | 禁止 |
| --- | --- | --- |
| 任务条 | 当前办理项、状态、责任角色 | 只显示内部编号 |
| 对象摘要块 | 住客、住宿单、房间床位、金额依据 | 把系统已知信息放进输入框 |
| 只读摘要块 | 来源、主体、财务、证据、上游关系 | 让用户重复填写 |
| 对象选择器 | 房间、床位、主体、联系人 | 手填对象名称 |
| 分段控件 | 住宿类型、收付方向、金额阶段 | 长下拉塞满屏幕 |
| 证据块 | 上传、缺失、驳回、过期和补交路径 | 只显示“未完成” |
| 财务边界块 | 金额、币种、阶段、财务状态 | 宿舍域显示正式收付款事实 |
| 阻断原因块 | 缺证据、缺权限、缺床位、财务驳回 | 只显示错误码 |
| 下一步承接块 | 下一责任角色、办理项、只读记录 | 只显示“成功” |

## 三语言布局规则

- 中文、俄语、吉语共用同一信息架构。
- `label` 可本地化和缩短，`value` 稳定中立。
- 俄语和吉语长文案必须允许两行显示；超过两行进入展开说明。
- 主按钮、金额、证据状态和阻断原因不得被长文案遮挡。
- 空态、错误、阻断、下一步不得 fallback 到内部 key、技术词或旧中文状态。

## 高保真准入

页面进入高保真前必须满足：

- 有 `09-scenario-step-field-contracts.md` 对应的 `scenarioKey` 和 `stepKey`。
- 有 `08-state-action-transition-contract.md` 对应的合法动作。
- 有 `11-field-key-and-option-set-contract.md` 对应的字段 key、控件类型、选项集、稳定 value 和三语言 label。
- 有 `12-minimal-input-and-autofill-policy.md` 对应的少填、自动带出和自由文本边界。
- 有 `13-screen-field-blueprint.md` 对应的页面字段蓝图；未进入蓝图的页面先补蓝图，不直接画高保真。
- 明确 `primaryBusinessObject`、`requiredReadContext`、`editableInputs`、`fixedSelections`、`financialContext`、`evidenceMaterials`、`legalActions`、`handoffSummary`、`searchReadModel`、`languageKeys`。
- 明确三语言标题、主按钮、字段、状态、错误、空态、证据、金额、下一步。
- 明确当前页面是否可提交、为何不可提交、提交后去哪。
- 明确不改当前 runtime/surface，只作为 vNext 视觉方向或样板。

## 第一批样板屏

第一批高保真只建议做 6 个样板屏，不一次性画满 13 场景：

| 样板屏 | 对应步骤 | 验证重点 |
| --- | --- | --- |
| 今日待办/宿舍办理项队列 | `dormitory.work_item_queue` | 工作台密度、状态优先级、下一步 |
| 外部住宿客户接入与报价 | `lodging.inquiry_and_quote.external_source_to_intake`、`select_quote_room_bed` | 来源、主体、诉求、报价候选 |
| 房间床位选择 | `lodging.reservation_and_inventory_hold.hold_reservation_bed` | 对象选择器、床位状态、锁定 |
| 押金/收款财务承接 | `lodging.payment_deposit_and_guarantee.prepare_deposit_basis`、`prepare_payment_basis` | 金额、币种、收付方向、财务边界 |
| 入住确认 | `lodging.check_in_processing.verify_checkin_readiness`、`confirm_checkin` | 阻断、证据、交付确认 |
| 退住结算/退款扣减 | `lodging.checkout_and_settlement.submit_checkout_settlement`、`lodging.cancel_noshow_refund_intake.prepare_cancel_or_noshow_refund_basis` | 检查、扣减、退款、财务承接 |

这些样板屏的字段、阻断、主按钮和下一步以 `13-screen-field-blueprint.md` 为准。视觉稿不得新增合同外字段，也不得把对象选择器画成手填输入框。

## 已选融合方向

进入下一版原型时，不再继续沿用旧的三方向探索作为待选项。新的原型采用以下融合方向：

| 方向 | 性格 | 适用 |
| --- | --- | --- |
| Boardroom Ledger | 经营工作台、队列、压力、待办、资源回流 | 今日经营工作台和命令搜索入口 |
| Ivory Suite Command | 轻、现代、暖白、清晰办理节奏 | 来源接入、主体确认、房间床位选择、入住确认 |
| Titanium Settlement | 钛银、雾灰、金额层级、证据审计 | 押金/收款、退住结算、财务回执 |

三个气质合并为 **Executive Quiet Operations**。它不能使用花哨渐变、营销首页、装饰性大图、旧后台视觉、绿色状态体系或多语言同屏展示。

## 命令搜索体验

命令搜索是 vNext 宿舍移动端的主动办理入口之一，但它只负责发现对象和推荐办理项：

- 输入 `0906-1退房` 或 `0906-1退住`，识别床位 `B 座 0906-1`、住宿单、住客、押金余额和当前状态，推荐进入退住检查。
- 输入 `0906-1结算`，推荐进入结算依据。
- 输入 `0906-1恢复`，推荐进入床位恢复或资源回流。
- 输入 `欧亚物流入住`，推荐进入外部客户入住闭环。
- 输入 `欧亚物流押金`，推荐进入押金/收款财务承接。

搜索结果必须显示对象摘要、证据缺口、财务边界和下一步。搜索不得直接写住宿事实、财务事实或恢复床位状态。

## UI 验收问题

每个样板屏必须回答：

1. 我在办什么？
2. 当前业务对象是谁？
3. 系统已经带出了什么？
4. 我本次真正需要填什么？
5. 哪些只能选，不能手填？
6. 缺什么证据、床位、权限或财务承接？
7. 金额、币种、收付方向和财务状态是什么？
8. 主按钮为什么可点或不可点？
9. 提交后去哪里？
10. 中文、俄语、吉语是否都能放下且不遮挡？

## 当前结论

当前可以进入 **Executive Quiet Operations 融合方向的新原型重做**。旧 `outputs/workos-vnext/dormitory-ui-prototype/` 不提交、不继承、不作为验收件。下一版只做两个完整衔接场景，先通过人工设计验收，再决定是否把新的 `outputs/workos-vnext/` 原型单独提交。
