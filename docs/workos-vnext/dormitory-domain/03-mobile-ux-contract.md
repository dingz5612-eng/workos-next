# 宿舍移动端 UX 合同

## 设计锚点

本文件遵循总设计七层模型，定义宿舍经营域在移动端的用户体验合同。移动端一级入口仍为今日、工作项、搜索、我的；宿舍不是一级导航入口。来源接入通过 `DomainIntake`，写动作进入 `VNextExecutionItem`，只读摘要消费 `BusinessSummaryReadModel`，三语言表达遵循 `VNextLanguageContract`；本文件不修改当前 OAM、generated、runtime、surface 或 tests。

移动端页面必须消费 `09-scenario-step-field-contracts.md` 的字段分组、`11-field-key-and-option-set-contract.md` 的字段/选项、`12-minimal-input-and-autofill-policy.md` 的少填规则，以及 `08-state-action-transition-contract.md` 的合法动作。页面可以调整布局密度，但不得新增字段、隐藏必需证据、把动作塞入表单或把固定选择改成手填。

vNext 移动 UI 重设计方向以 `10-mobile-ui-redesign-direction.md` 为准。现有 WorkOSNext mobile surface UI 只作为问题审计对象，不作为视觉、布局、组件、色彩、字体、卡片风格或交互继承来源。

## 宿舍主路径

```text
今日/搜索
-> 来源卡
-> 主体解析卡
-> 住宿接入确认卡
-> 住宿办理项
-> 提交确认
-> 财务承接、下一办理项、等待回执或只读记录
```

```text
工作项
-> 宿舍办理项
-> 上游只读摘要
-> 当前输入/固定选择
-> 证据块
-> 财务边界块
-> 提交确认
-> 下一步承接
```

## 页面顺序

每个宿舍页面必须按以下顺序组织：

1. 我在办什么：住宿申请、住宿单、入住、续住、换房、退住、押金申请等。
2. 系统已带出什么：来源、主体、员工关系、房间床位、财务摘要、上游证据。
3. 我要填什么：本次真实输入或固定选择。
4. 缺什么：证据、主体解析、床位、财务承接、维修/清洁回执。
5. 财务边界：金额依据、币种、业务对象、收付方向、阶段语义。
6. 提交后去哪：下一办理项、等待财务、只读记录、追加修正。

每个页面必须能映射回 `09` 的 `fieldKeyGroups.requiredReadContext`、`editableInputs`、`fixedSelections`、`financialContext`、`evidenceMaterials`、`legalActions`、`handoffSummary`。每个字段必须能在 `11` 找到字段定义或选项集，每个输入必须通过 `12` 的少填策略。缺少任一组时，该页面不得进入正式体验评审。

## 卡片模式

| 卡片 | 必须显示 | 禁止 |
| --- | --- | --- |
| 来源卡 | 来源类型、渠道、诉求、初始证据、候选业务域 | 直接生成住宿单 |
| 主体解析卡 | 候选住客/企业/员工、匹配依据、重复风险 | 用姓名或手机号替代业务锚点 |
| 住宿接入确认卡 | 目标住宿类型、接入条件、证据、转入后办理项 | 提前占用床位 |
| 房间床位候选卡 | 房间、床位、状态、价格快照、风险 | 显示不可用资源为可选 |
| 住宿办理项卡 | 只读上下文、当前输入、固定选择、证据、财务边界 | 把流程动作放入字段 |
| 财务边界卡 | 金额、币种、收付方向、阶段、财务状态 | 确认正式收付款 |
| 下一步承接卡 | 下一责任角色、等待回执、阻断原因、已完成记录 | 只显示“成功” |

## 角色体验

### 一线经办人

- 默认看今日和工作项。
- 优先处理可立即办理、缺证据、等待财务、床位阻断。
- 页面必须减少重复录入，系统已知的来源、主体、床位、财务状态只读展示。

### 财务人员

- 只从等待财务的办理项进入。
- 读取宿舍金额依据、业务对象和证据。
- 确认正式财务事实后输出财务结果摘要。

### 主管/经理

- 处理阻断、超时、资源不可用、退住异常、换房冲突。
- 只能转交、升级、拍板前置判断或回责任办理项。

### 管理层

- 只看宿舍经营摘要、风险、趋势和拍板入口。
- 拍板必须形成 `ManagementDecisionRecord` 并回宿舍或财务办理。

### 治理/审计岗

- 查看来源、主体、住宿单、床位、证据、财务回执、修正链。
- 主对象问题回共享治理，业务事实问题发起追加修正。

## 固定选择与对象选择器

必须使用对象选择或固定选项的内容：

- 房间和床位。
- 入住、续住、换房、退住动作。
- 证据类型。
- 金额阶段语义。
- 币种。
- 收付方向。
- 财务承接状态。
- 阻断原因。

不得退化为手填。

当移动端空间不足时，优先保留业务对象、金额币种、证据状态、阻断原因和主按钮；长说明进入可展开区，但不得遮挡或压缩主操作。

## 少填体验

移动端默认不让用户重复录入系统已知信息：

- 来源、主体、企业、员工关系、房间、床位、价格快照、财务回执和证据状态优先只读带出。
- 房间、床位、主体、联系人、住客和企业必须用对象选择器。
- 状态、原因、币种、证据类型、阻断原因和责任域必须用权威选项集。
- 自由文本只作为受控原因后的可选补充，不作为事实主来源。
- 金额必须和币种、收付方向、金额阶段、业务对象同屏。

第一批页面蓝图以 `13-screen-field-blueprint.md` 为准；未进入蓝图或未通过 `09/11/12` 的页面不得直接进入高保真。

## 三语言体验

每个页面必须声明：

- `titleKey`
- `descriptionKey`
- `primaryActionKey`
- `statusKey`
- `errorKey`
- `evidenceKey`
- `financeKey`
- `nextStepKey`

中文、俄语、吉语均必须覆盖。俄语和吉语长文案允许换行和短 label，不得遮挡主按钮、金额、证据状态和下一步。

进入高保真前，页面还必须通过 `10-mobile-ui-redesign-direction.md` 和 `13-screen-field-blueprint.md` 的高保真准入：业务字段、合法动作、财务边界、证据、阻断、少填规则和三语言都先在合同中成立，再进入视觉稿。

## 搜索体验

用户可搜索：

- 住客姓名、企业名、员工、房间、床位、住宿单、来源、电话号码、状态、费用依据。

搜索结果必须区分：

- 只读查看。
- 可办理动作。
- 需要权限或证据的阻断。
- 等待财务或上游的事项。

搜索结果不得直接写事实。
