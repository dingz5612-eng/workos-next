# 宿舍经营域执行流

## 设计锚点

本文件遵循总设计七层模型，把宿舍经营域动作落到 `DomainIntake`、`VNextExecutionItem`、财务承接、`BusinessSummaryReadModel` 和 `VNextLanguageContract` 上。所有写动作必须进入办理项/WorkItem 和提交确认；本文件不修改当前 OAM、generated、runtime、surface 或 tests。

本文件描述业务流向，不直接定义字段。每条执行流落地时，必须同时满足 `08-state-action-transition-contract.md` 的状态动作合同和 `09-scenario-step-field-contracts.md` 的场景步骤字段合同。

## 外部住宿客户

```text
SourceAttribution：广告/推荐/电话/企业联系人
-> SubjectResolution：外部主体、组织、联系人
-> DomainIntake：dormitory.external_stay_intake
-> VNextExecutionItem：住宿申请办理项
-> 房间床位候选
-> 价格快照和费用依据
-> 押金申请或收款依据
-> 财务承接办理项
-> 财务回执只读摘要
-> 入住办理项
-> 在住 BusinessSummaryReadModel
```

关键输入：入住日期、预计周期、人数、房型/床位偏好、联系方式、证据。

失败路由：

- 主体重复或身份冲突：回共享治理。
- 缺证据：等待证据。
- 无可用床位：进入资源处理办理项。
- 财务承接失败：等待财务或回宿舍修正金额依据。

字段合同锚点：外部客户接入、询价报价、预订锁定、押金收款、入住办理分别对应 `09` 中 `lodging.inquiry_and_quote`、`lodging.reservation_and_inventory_hold`、`lodging.payment_deposit_and_guarantee`、`lodging.check_in_processing`。

## 内部员工住宿

```text
SourceAttribution：内部申请/管理指派
-> SubjectResolution：员工主体
-> 人事行政只读员工关系摘要
-> DomainIntake：dormitory.employee_stay_intake
-> VNextExecutionItem：员工住宿申请办理项
-> 房间床位分配
-> 内部结算依据或费用依据
-> 入住确认
-> 员工住宿摘要只读回人事行政
```

边界：

- 员工关系归人事行政。
- 住宿分配、入住、续住、退住归宿舍域。
- 工资扣减、报销、支付归财务域。

字段合同锚点：内部员工住宿复用 `09` 的共享字段字典，必须读取 `employee_relation.summary`，不得要求一线经办人手填员工关系、岗位、工资或人事状态。

## 企业客户住宿

```text
SourceAttribution：企业联系人/合作方/渠道
-> SubjectResolution：企业主体、联系人、住客候选
-> DomainIntake：dormitory.corporate_stay_intake
-> VNextExecutionItem：企业住宿接入办理项
-> 企业住宿方案、房间床位批量候选
-> 价格快照、协议/费用依据
-> 财务承接或合同承接
-> 批量入住办理项
```

关键要求：

- 企业主体和实际住客主体分开。
- 企业协议、渠道佣金和结算只形成依据，不形成正式财务事实。
- 批量入住必须逐个住客可追踪，不得只用企业名替代住客锚点。

字段合同锚点：企业客户住宿对应 `09` 中 `lodging.channel_corporate_customer`，企业主体、联系人和实际住客必须拆成不同字段锚点。

## 入住办理

```text
住宿单
-> 入住办理项
-> 读取主体、房间床位、财务回执、证据
-> 身份/协议/钥匙或交付确认
-> 提交确认
-> 入住事件
-> 床位 occupied
-> 在住摘要
```

阻断：

- 财务要求未满足。
- 身份或员工关系未满足。
- 房间床位状态不允许入住。
- 必需证据缺失。

## 续住

```text
在住住宿单
-> 续住办理项
-> 读取当前住宿、床位、余额/押金摘要
-> 生成续住费用依据
-> 财务承接
-> 续住确认
-> 更新住宿周期和摘要
```

续住不得覆盖原入住事实；必须形成续住事件和审计链。

## 换房换床

```text
在住住宿单
-> 换房换床接入
-> 目标房间床位候选
-> 换房办理项
-> 原床位检查
-> 目标床位分配
-> 费用差额依据
-> 财务承接或无需财务回执
-> 换房事件
```

边界：

- 原床位未检查不得恢复可经营。
- 差额只是金额依据，正式收退归财务。

## 退住结算

```text
住宿单
-> 退住办理项
-> 房间床位检查
-> 退住费用/扣减/退款依据
-> 财务承接结算
-> 财务结果摘要
-> 关闭住宿单
-> 床位进入 cleaning/maintenance/available
```

阻断：

- 房间床位检查未完成。
- 维修或清洁协同未完成。
- 退款/扣减依据缺业务对象、币种或证据。

## 押金/退款

```text
住宿单或退住结算依据
-> 押金/退款/扣减依据
-> 财务承接办理项
-> 财务事实
-> 财务结果摘要
-> 宿舍只读消费
```

宿舍域不得显示“已退款”“已收押金”作为自有事实，只能显示财务回执摘要。

## 异常修正

```text
已完成只读记录
-> 发起追加修正
-> 修正办理项
-> 提交确认
-> 修正事件
-> 摘要更新
-> 审计保留原事实和修正事实
```

适用场景：

- 入住日期或床位错误。
- 费用依据缺币种或对象。
- 证据错绑。
- 财务承接失败后业务依据需要修正。
- 退住检查结果补充。

## 三语言执行要求

每条执行流必须显示：

- 当前在办什么。
- 系统已带出什么。
- 本次需要填写或选择什么。
- 缺什么证据、权限、上游或财务承接。
- 提交后去哪。

以上内容必须覆盖中文、俄语、吉语。

页面字段、按钮、阻断、证据和下一步的三语言 key 必须来自 `09-scenario-step-field-contracts.md`，不得由页面临时拼接。
