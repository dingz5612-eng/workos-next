# 验收合同

## 设计锚点

本文件遵循七层模型和 `VNextLanguageContract`。验收只判断 vNext 蓝图是否自洽；任何写入必须进入办理项/WorkItem 和提交确认。

## 文件级验收

必须成立：

- 所有文件都指向同一套七层模型。
- 所有用户可见表达都指向三语言合同。
- 不存在旧结构残留。
- 不把来源入口限定到宿舍业务。
- 不把共享治理写成业务事实汇总口。
- 不让宿舍样板反向决定总架构。
- 不让管理驾驶舱直接办理、关闭或改写业务异常。

## 场景一：外部住宿客户

路径：

```text
来源归因
-> 主体解析
-> DomainIntake：住宿接入
-> 住宿办理项
-> 财务承接
-> 入住
```

责任域：来源归因、共享治理、销售与宿舍经营、合同与财务。

输入：广告/推荐/电话来源、客户主体信息、住宿诉求、初始证据。

输出：住宿单、房间床位状态、费用依据、押金申请、财务结果摘要、入住记录。

失败路由：主体未解析回共享治理；床位不可用进入资源处理；押金未承接等待财务；证据缺失等待证据。

证据产物：来源记录、主体解析记录、住宿办理项提交确认、财务承接回执、审计链。

通过标准：来源不生成住宿事实；主体归共享治理；住宿单归宿舍经营；押金和收款归财务；页面三语言可办理。

## 场景二：维修客户

路径：

```text
来源归因
-> 主体/车辆解析
-> DomainIntake：维修接待
-> 维修办理项
-> 费用依据
-> 财务承接
```

责任域：来源归因、共享治理、维修与配件服务、合同与财务。

输入：客户维修需求、车辆信息、故障描述、初始证据。

输出：维修接待、诊断/施工/质检事件、费用依据、财务承接状态。

失败路由：车辆未解析回共享治理；费用依据不完整回维修办理项；财务证据不足等待财务证据。

证据产物：来源记录、车辆解析记录、维修办理项、费用依据、财务承接回执。

通过标准：来源不生成维修单；车辆主对象归共享治理；维修事件归维修域；收付款归财务域；维修状态和费用三语言可读。

## 场景三：内部员工住宿

路径：

```text
内部申请来源
-> 员工关系摘要
-> DomainIntake：员工住宿接入
-> 住宿办理项
-> 入住确认
```

责任域：来源归因、共享治理、人事行政、销售与宿舍经营、合同与财务。

输入：内部申请、员工主体、员工关系摘要、住宿需求。

输出：住宿单、入住确认、员工住宿只读摘要、必要财务或内部结算回执。

失败路由：员工关系缺失回人事行政；主体未解析回共享治理；床位不可用进入资源处理。

证据产物：内部申请来源、员工关系摘要、住宿办理项、入住确认审计。

通过标准：人事行政只拥有人事关系；住宿服务动作归宿舍经营；员工住宿摘要只读回人事行政；三语言说明“不由人事处理住宿服务动作”。

## 场景四：配件需求

路径：

```text
来源归因
-> 主体解析
-> DomainIntake：配件需求接入
-> 配件履约办理项
-> 费用依据
-> 财务承接
```

责任域：来源归因、共享治理、维修与配件服务、合同与财务。

输入：客户或内部配件需求、主体信息、配件规格、证据。

输出：配件履约动作、库存变化摘要、费用依据、财务承接结果。

失败路由：主体未解析回共享治理；规格不完整等待证据；库存不足进入配件履约阻断；财务失败等待财务。

证据产物：来源记录、主体解析、配件履约办理项、库存变化摘要、财务回执。

通过标准：来源不直接形成配件履约事实；配件动作归维修与配件服务域；财务事实归合同与财务域；配件状态三语言可读。

## 场景五：重复主体或车辆

路径：

```text
来源或业务对象
-> 重复候选
-> 差异提示
-> 合并建议办理项
-> 主对象或关系修正
```

责任域：共享治理。

输入：来源、主体候选、车辆候选、差异字段、证据。

输出：主对象、关系修正、合并建议结果、风险回执。

失败路由：证据不足等待证据；不可合并输出不可合并原因；涉及业务事实时回责任业务域。

证据产物：重复候选、差异提示、合并建议办理项、审计链。

通过标准：共享治理只处理主对象和关系；不合并业务事件；不改写财务事实；不可合并原因三语言可读。

## 场景六：管理分析与拍板

路径：

```text
各域 BusinessSummaryReadModel
-> 管理分析只读视图
-> ManagementDecisionRecord
-> 回业务域或财务域办理项
```

责任域：读模型与分析、管理驾驶舱、目标业务域或财务域。

输入：各域只读摘要、风险回执、财务结果摘要、审计追踪。

输出：只读分析产物、管理拍板记录、后续责任域办理项。

失败路由：异常处理回责任业务域；财务处理回合同与财务；主体问题回共享治理。

证据产物：分析视图来源、拍板记录、后续办理项、审计链。

通过标准：分析不写事实；拍板不直接处理异常；异常回到责任域办理；三语言明确“只读分析”和“回责任域办理”。

## 三语言验收

必须覆盖：

- 中文 `zh-CN`、俄语 `ru-RU`、吉语 `ky-KG`。
- 页面标题、按钮、字段、提示、错误、状态、空态、加载态。
- 来源卡、主体解析卡、转域确认卡、办理项、财务边界块、分析只读卡。
- 金额、币种、支付方式、退款方式、押金、核销、核算。
- 展示 label 和提交 value 分离。
- 长文案在移动端不溢出、不遮挡、不挤压关键操作。

不通过标准：

- 任一语言缺少关键按钮、状态、错误或金额表达。
- 页面显示 enum/status/action 稳定 value。
- fallback 到内部 key、技术词、旧中文状态或测试样例。

## 全局边界检查

| 边界 | 必须成立 |
| --- | --- |
| 来源归因 | 只记录入口和诉求，不写业务事实。 |
| 共享治理 | 只管主对象、关系、去重和共享状态。 |
| 业务域 | 只拥有本域申请、事件、状态、资源、摘要和金额依据。 |
| 财务域 | 唯一拥有正式财务事实。 |
| 执行层 | 所有写动作进入办理项和提交确认。 |
| 读模型与分析 | 只读消费摘要，不处理异常。 |
| 体验层 | 不发明事实，不绕过 runtime。 |
| 三语言合同 | label 本地化，value 稳定中立，三语言齐备。 |

## UX 检查

每个关键页面必须回答：

1. 我在办什么？
2. 这个来源、主体或对象是什么？
3. 系统已经带出了什么？
4. 我本次真正需要填写或选择什么？
5. 哪些内容只读？
6. 缺什么证据、权限、上游或财务承接？
7. 金额处于依据、申请、承接中、已定真还是已核算？
8. 提交后谁处理、去哪里看、下一步是什么？
9. 当前语言下是否能完整理解标题、按钮、错误和下一步？

## OAM 兼容检查

通过本验收不等于当前 OAM GO，不等于可发布，不等于可试运行。

落地前必须另行确认：

- 是否进入当前 Source Authority。
- 是否进入 Experience Authority。
- 是否需要 language model。
- 是否需要 generated 合同。
- 是否影响 runtime、surface、tests。
- 是否需要真实浏览器和 Evidence Root 验证。
