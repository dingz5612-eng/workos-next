# 三语言与本地化合同

## 设计锚点

本文件定义 `VNextLanguageContract`。它横向约束移动端体验、办理项、读模型、错误、证据、金额和管理分析表达。三语言为中文、俄语、吉语，面向吉尔吉斯斯坦比什凯克业务场景。

本合同不改变七层模型：来源归因层、共享治理层、业务域事实层、财务真值层、执行层、读模型与分析层、体验层。任何语言选择、翻译缺失、fallback 或本地化配置，都不得绕过办理项/WorkItem 和提交确认写入事实。

## 支持语言

| 语言 | locale | 使用场景 |
| --- | --- | --- |
| 中文 | `zh-CN` | 管理、内部设计、部分华语员工和后台运营。 |
| 俄语 | `ru-RU` | 比什凯克常用业务沟通和员工操作。 |
| 吉语 | `ky-KG` | 本地员工、客户和合规场景。 |

所有用户可见页面必须至少支持这三种语言。任何页面、按钮、状态、错误、空态、加载态、证据名称、金额说明和财务阶段，如果缺少其中一种语言，视为体验合同不完整。

## label/value 分离

稳定值：

- enum、status、action、reason、domain、currency、paymentMethod 必须使用语言无关的稳定 value。
- value 不得使用中文、俄语或吉语自然语言。
- value 不得直接展示给用户。

显示文案：

- 用户只看到三语言 label。
- label 通过 `displayKey`、`fieldKey`、`statusKey`、`actionKey`、`errorKey`、`emptyStateKey`、`evidenceKey` 渲染。
- 缺失翻译只能进入受控 fallback，不得页面私自拼接。

## 显示键合同

每个用户可见对象必须声明：

- `titleKey`：页面或卡片标题。
- `descriptionKey`：一句业务话说明正在办什么。
- `fieldKeys`：字段 label。
- `actionKeys`：按钮和合法动作。
- `statusKeys`：状态、阶段和同步状态。
- `reasonKeys`：阻断原因、失败路由、不可处理原因。
- `evidenceKeys`：证据名称、证据状态、上传或绑定错误。
- `financeKeys`：金额、币种、收付方向、押金、退款、核销、核算。
- `emptyStateKey` 和 `loadingKey`：空态和加载态。

## 移动端约束

- 长文案必须允许换行，不能遮挡主按钮、金额、证据状态或下一步。
- 俄语和吉语文案可能长于中文，按钮必须允许短 label 或二行布局。
- 页面不能依赖颜色单独表达状态，三语言状态文案必须可读。
- 错误提示必须说明缺什么、去哪补、谁处理、处理后下一步是什么。
- 内部 ID、payload hash、definitionId、raw code 不得作为主标题或错误正文。

## 财务语言

金额类表达必须同时显示：

- 金额
- 币种
- 业务对象
- 收付方向
- 阶段语义：依据、申请、承接中、已定真、已核销、已核算
- 应收/应退、已收/已退、本次金额、差额

禁止只显示数字或只显示金额字段名。财务页面和业务域页面必须用三语言说明“这是金额依据、押金申请、财务事实还是只读回执”。

## fallback 规则

受控 fallback 顺序：

1. 当前 locale 的正式 label。
2. 当前 locale 的短 label。
3. 受控备用语言 label，并显示缺失翻译标记给治理/配置人员。
4. 阻断页面发布或进入验收失败。

不得 fallback 到稳定 value、内部 key、英文技术词、旧中文状态或测试样例。

## 验收

三语言验收必须覆盖：

- 页面标题、按钮、字段、提示、错误、状态、空态、加载态。
- 来源卡、主体解析卡、转域确认卡、办理项、财务边界块、分析只读卡。
- 金额、币种、支付方式、退款方式、押金、核销、核算。
- 长文案在移动端不溢出、不遮挡、不挤压关键操作。
- 展示文案和提交 value 分离。
